Retrieval-Augmented Generation (RAG) is the mechanism Voice Agent uses to ground LLM responses in your actual data. Rather than relying solely on the model's training knowledge, every chat completion call is preceded by a semantic search that pulls the most relevant passages from your uploaded documents, the current session's file attachments, and the session's own conversation history. Those passages are injected into the LLM prompt as a third system message, letting Gemini answer with specificity about your content without any fine-tuning.

## Embedding model

Embeddings are generated by `EmbeddingService` in `app/services/embedding_service.py`, which wraps the Google Generative AI SDK.

```python
class EmbeddingService:
    def __init__(self):
        genai.configure(api_key=os.getenv("GEMINI_API_KEY"))
        self.model = "models/gemini-embedding-001"

    async def get_embeddings(self, text: str) -> List[float]:
        result = genai.embed_content(
            model=self.model,
            content=text,
            task_type="retrieval_document",
            output_dimensionality=3072  # matches DB schema
        )
        return result['embedding']
```

| Property | Value |
|---|---|
| **Model** | `models/gemini-embedding-001` |
| **Dimensions** | **3072** (explicitly set via `output_dimensionality`) |
| **Task type** | `retrieval_document` |
| **DB column type** | `pgvector` `Vector(3072)` |

The same model and dimension are used for both indexing (when documents or messages are stored) and querying (when a user sends a message), ensuring cosine distances are directly comparable.

## Data sources searched

`search_documents()` in `app/services/llm_service.py` queries three independent tables in a single call and merges the results:

| Source table | What it contains | Filter applied |
|---|---|---|
| `document_master` | Admin-uploaded knowledge-base documents (global) | None — all active documents are candidates |
| `chat_attachments` | Files uploaded by the user within a specific chat turn | Filtered to the current `user_id` and `session_id`; `is_deleted = 0` |
| `chats` | Previous conversation turns (user + assistant messages) | Filtered to the current `user_id` and `session_id`; `is_deleted = 0` |

<Note>
  `chat_attachments` and `chats` are only searched when both `user_id` and `session_id` are provided. For anonymous or session-less calls only `document_master` is queried.
</Note>

## Search algorithm

The function signature is:

```python
async def search_documents(
    db: AsyncSession,
    query_text: str,
    user_id: Optional[int] = None,
    session_id: Optional[int] = None,
    top_k: int = 5,
    fetch_multiplier: int = 3
)
```

<Steps>
  <Step title="Generate query embedding">
    `embedding_service.get_embeddings(query_text)` converts the (potentially rewritten) user query into a 3072-dimensional float vector.
  </Step>
  <Step title="Fetch top-N candidates from each source">
    Each source is queried for `top_k × fetch_multiplier` rows (default: `5 × 3 = 15` per source). Fetching more than the final `top_k` from each source gives the global reranker enough material to promote the best cross-source results.
  </Step>
  <Step title="Compute cosine distance with pgvector">
    All three queries use the pgvector `<=>` (cosine distance) operator. Lower distance = higher semantic similarity. The query embedding is cast to the `vector` type inline:

    ```sql
    SELECT
        'document_master' AS source,
        id,
        file_name        AS title,
        content          AS text,
        embedding <=> CAST(:embedding AS vector) AS distance
    FROM document_master
    ORDER BY embedding <=> CAST(:embedding AS vector)
    LIMIT :limit
    ```

    The `chat_attachments` query additionally joins `chats` to enforce the session/user filter:

    ```sql
    SELECT
        'chat_attachments' AS source,
        ca.id,
        ca.file_name  AS title,
        ca.file_text  AS text,
        ca.embedding <=> CAST(:embedding AS vector) AS distance
    FROM chat_attachments ca
    JOIN chats c ON ca.chat_id = c.id
    WHERE c.user_id    = :user_id
      AND c.session_id = :session_id
      AND ca.is_deleted = 0
    ORDER BY ca.embedding <=> CAST(:embedding AS vector)
    LIMIT :limit
    ```
  </Step>
  <Step title="Merge all results">
    Rows from all three sources are collected into a single Python list. Each row is a dict with keys `source`, `id`, `title`, `text`, and `distance`.
  </Step>
  <Step title="Global rerank by distance">
    The merged list is sorted ascending by `distance` (lowest cosine distance = most similar). This promotes the globally most-relevant passages regardless of which source they came from.
  </Step>
  <Step title="Return final top_k results">
    The sorted list is sliced to `top_k` (10 in `chatConversation`). These records are returned to the caller as `relevant_docs`.
  </Step>
</Steps>

## Integration with the LLM

After `search_documents()` returns, `llm_call()` passes the retrieved passages as a third message in the LiteLLM messages array:

```python
response = await acompletion(
    model="gemini/gemini-2.5-flash",
    messages=[
        {"role": "system",  "content": system_instructions},       # 7 prompt templates
        {"role": "user",    "content": f"Prompt: {prompt}"},       # user query
        {"role": "system",  "content": f"Relevant Text to the Query:{relevant_docs}"}  # RAG context
    ],
    stream=stream,
)
```

The `relevant_docs` list is the raw Python list of dicts from `search_documents()`. Each dict includes `source`, `title`, `text`, and `distance`, giving the model enough metadata to attribute its answer.

## Query resolution

Before the RAG search runs, `resolve_query_with_history()` in `app/services/ai_chat_service.py` rewrites follow-up queries into standalone questions. This is critical for embedding quality — a query like *"explain that again"* would produce a poor embedding and retrieve irrelevant documents without rewriting.

<Tip>
  Upload documents via `POST /api/upload_documents` (or the equivalent document extraction endpoint) to populate `document_master` before users start querying. Without documents in `document_master`, RAG context will only come from the session's own chat history and attachments.
</Tip>
