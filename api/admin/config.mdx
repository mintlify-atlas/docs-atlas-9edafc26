Voice Agent includes a runtime configuration system that lets administrators manage application settings directly in the database without redeployment. Configuration is organised in two tiers: a **Config Group** acts as a named namespace (e.g. `"LLM Settings"`, `"Voice Pipeline"`), and each group contains one or more **Config Parameters** — individual key-value entries identified by a `name` and a stable `paramUniqueId`. Both tiers support soft-deletion and maintain full audit trails with `createdBy`/`updatedBy` fields. All endpoints require a valid Bearer token and use `POST` with the `DataRequest` envelope.

<Note>
  All request bodies must be wrapped in `{"data": {...}}`. All responses follow the standard `APIResponse` envelope. Pagination on list endpoints is controlled by `skip` and `limit` query parameters.
</Note>

## Response envelope

```json
{
  "dataResponse": {
    "returnCode": 0,
    "responseDateTime": "2024-01-15T10:30:00",
    "description": "..."
  },
  "data": { ... }
}
```

| `returnCode` | Meaning       |
|-------------|---------------|
| `0`         | SUCCESS       |
| `2`         | NO_DATA_FOUND |
| `10`        | NOT_FOUND     |
| `16`        | BAD_REQUEST   |

## Data model

```
config_group
    │
    ├─ id (PK)
    ├─ name          (unique)
    ├─ description
    ├─ groupUniqueId (auto-generated: GROUP_<NAME_UPPERCASED>)
    │
    └─── config_param (one-to-many via config_group_id)
             │
             ├─ id (PK)
             ├─ name          (unique)
             ├─ description
             ├─ configGroupId (FK → config_group.id)
             └─ paramUniqueId (auto-generated: <GROUP_NAME>_<PARAM_NAME>)
```

A `ConfigGroup` is a logical container — think of it as a configuration namespace. Each `ConfigParam` inside it is an individual setting entry. The `paramUniqueId` embeds the parent group name, making it self-documenting (e.g. `LLM_SETTINGS_MODEL_NAME`). Both unique IDs are generated automatically at creation time and cannot be set by the caller.

<Tip>
  Use `groupUniqueId` and `paramUniqueId` as stable identifiers in your application code. Because they are derived from names, changing a name via the edit endpoint does **not** update the unique ID — store the ID returned at creation time.
</Tip>

## Config Group endpoints

### Add or edit a config group

Creates a new config group (`id: 0`) or updates an existing one (pass the numeric `id`). On creation, `groupUniqueId` is automatically generated as `GROUP_<NAME_UPPERCASED>` and cannot be overridden.

```
POST /addEditConfigGroup
```

**Authentication:** Bearer token required.

#### Request body

<ParamField body="id" type="integer" default="0">
  Pass `0` to create a new config group. Pass the existing integer primary key to update it.
</ParamField>

<ParamField body="name" type="string" required>
  Unique name for the config group. Returns `400 Bad Request` if a non-deleted group with this name already exists.
</ParamField>

<ParamField body="description" type="string" required>
  Description of what this group of parameters configures.
</ParamField>

<ParamField body="groupUniqueId" type="string">
  Optional. Ignored on create (auto-generated). May be supplied on update but the service does not persist changes to this field — `groupUniqueId` is set once at creation.
</ParamField>

<ParamField body="isDeleted" type="integer" default="0">
  Soft-delete flag. Defaults to `0`.
</ParamField>

#### Response

Returns `APIResponse` with `data` as the created or updated `ConfigGroup` object. Both create and update return `returnCode: 0` (SUCCESS).

#### Examples

**Create a new config group**

```bash
curl -X POST https://api.example.com/addEditConfigGroup \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "id": 0,
      "name": "LLM Settings",
      "description": "Parameters for the language model"
    }
  }'
```

```json
{
  "dataResponse": {
    "returnCode": 0,
    "responseDateTime": "2024-01-15T10:30:00",
    "description": "Config group created successfully."
  },
  "data": {
    "id": 3,
    "name": "LLM Settings",
    "description": "Parameters for the language model",
    "groupUniqueId": "GROUP_LLM_SETTINGS",
    "isDeleted": 0,
    "createdOn": "2024-01-15T10:30:00",
    "createdBy": 1,
    "updatedOn": "2024-01-15T10:30:00",
    "updatedBy": 1,
    "deletedOn": null,
    "deletedBy": null
  }
}
```

**Update an existing config group**

```bash
curl -X POST https://api.example.com/addEditConfigGroup \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "id": 3,
      "name": "LLM Settings",
      "description": "Language model inference parameters"
    }
  }'
```

### Delete a config group

Soft-deletes a config group by its numeric primary key. The `data` field of the request envelope accepts an integer directly (not a nested object).

```
POST /deleteConfigGroup
```

**Authentication:** Bearer token required.

#### Request body

<ParamField body="data" type="integer" required>
  The integer primary key of the config group to delete. Unlike other endpoints, the `data` value is a bare integer, not an object: `{"data": 3}`.
</ParamField>

#### Response

Returns `APIResponse` with `returnCode: 0` and `data` as the soft-deleted `ConfigGroup` object. Returns `404 Not Found` if the group does not exist.

#### Example

```bash
curl -X POST https://api.example.com/deleteConfigGroup \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"data": 3}'
```

```json
{
  "dataResponse": {
    "returnCode": 0,
    "responseDateTime": "2024-01-15T11:00:00",
    "description": "Config group with ID 3 marked as deleted successfully."
  },
  "data": {
    "id": 3,
    "name": "LLM Settings",
    "description": "Language model inference parameters",
    "groupUniqueId": "GROUP_LLM_SETTINGS",
    "isDeleted": 1,
    "createdOn": "2024-01-15T10:30:00",
    "createdBy": 1,
    "updatedOn": "2024-01-15T11:00:00",
    "updatedBy": 1,
    "deletedOn": "2024-01-15T11:00:00",
    "deletedBy": 1
  }
}
```

<Warning>
  Deleting a config group does **not** cascade to its child `ConfigParam` records. Any parameters belonging to the deleted group will become orphaned. Delete or reassign child parameters before deleting the group.
</Warning>

## Config Param endpoints

### Add or edit a config param

Creates a new config parameter (`id: 0`) or updates an existing one. On creation, `paramUniqueId` is auto-generated by combining the parent group's name with the parameter name: `<GROUP_NAME>_<PARAM_NAME>` (both uppercased, spaces replaced with `_`).

```
POST /addEditConfigParam
```

**Authentication:** Bearer token required.

#### Request body

<ParamField body="id" type="integer" default="0">
  Pass `0` to create a new parameter. Pass the existing integer primary key to update it.
</ParamField>

<ParamField body="name" type="string" required>
  Unique name for this parameter. Returns an error if a non-deleted parameter with this name already exists.
</ParamField>

<ParamField body="description" type="string" required>
  Short description of what this parameter controls.
</ParamField>

<ParamField body="configGroupId" type="integer" required>
  Primary key of the parent config group. The group must exist and must not be soft-deleted, as `paramUniqueId` generation requires reading the group's name.
</ParamField>

<ParamField body="paramUniqueId" type="string">
  Optional on create (auto-generated). On update, if provided, the service will persist this value — use with care since `paramUniqueId` is intended to be a stable identifier.
</ParamField>

<ParamField body="isDeleted" type="integer" default="0">
  Soft-delete flag. Defaults to `0`.

#### Response

## Runtime configuration workflow

The configuration system is designed for zero-downtime settings updates. The recommended pattern for using it in application code:

1. **At startup** — load all required parameters by calling `getAllConfigParam` and index them by `paramUniqueId`.
2. **At runtime** — call `getSpecificConfigParam` to fetch the latest value of a setting on-demand, bypassing any in-process cache.
3. **To change a setting** — call `addEditConfigParam` with the parameter's `id` and the updated `description` field (or extend the schema with a `value` column in your deployment). No restart required.
4. **To retire a setting** — call `deleteConfigParam` to soft-delete it. The application code should gracefully fall back to a default if a parameter returns NO_DATA_FOUND.

<Note>
  The current schema stores configuration metadata (`name`, `description`, `paramUniqueId`) but not a freeform `value` column. In practice, the `description` field or an application-layer extension stores the actual runtime value associated with each parameter key.
</Note>
